# M41.7 — DELIVERABLE VERIFICATION CONTRACT

The mission-aware contract that replaced "audit the assistant's reply" with "audit the actual deliverable". This document is the normative spec for how M41 document and website missions are verified. It extends — never replaces — the existing self-verification pipeline (`src/lib/verification/pipeline.ts`) and the existing deterministic mission verifiers (`src/lib/riishe/mission/verifiers.ts`).

## 1. The two verification layers

| Layer | What it audits | Where it runs | Verdict authority |
| --- | --- | --- | --- |
| **Hosted mission-aware audit** | the EXTRACTED DELIVERABLE content (actual file bytes, not the reply wrapper) | inside the coding turn, via the SAME `verifyAndCorrect` loop | advisory + required when enabled: its honest status feeds `requireSelfVerification` (failed/unverified still blocks) |
| **Deterministic persisted-deliverable gate** | the REAL persisted `CodeFile` rows after the specialist job completes | the mission executor → pure verifiers | authoritative for the objective facts (existence, structure, references, citations); it can never be overridden upward |

Rules that did not change:
- a failed or unavailable hosted verifier is never a PASS;
- an absent persisted snapshot is `needs_correction`, never `verified`;
- verifiers never upgrade; missing evidence is `needs_correction` or `failed` with concrete reasons;
- the verification criteria live ONLY in the mission ledger — a specialist cannot read, infer, or alter its own acceptance contract (the context crosses the delegation boundary as a server-only third parameter; the model-called tool schema has no mission field).

## 2. The trusted context (`MissionVerificationContext`)

Built by the executor from the mission ledger ONLY:

```text
missionId, taskId, taskKind ('document-draft'|'code-build'),
deliverableKind ('document'|'website'|'code'),
deliverablePath, requiredPaths[], requiredSections[],
requireCitations, sources[{index,url,title}]   ← handoffSourceRefs(): the EXACT
                                                 numbered list the consumer's
                                                 handoff pack carried
minDeliverableChars (400), maxDeliverableChars (200,000)
```

- source URLs are `safeSourceUrl`'d (query strings stripped) — no ids/tokens/secrets;
- serialization is bounded (`VERIFY_CONTEXT_LIMITS.serializedChars` = 4000);
- the worker-side parser is shape-checked: malformed or forged input parses to `null` (mission framing disabled) and can never fabricate a weaker contract — forged `javascript:` sources are dropped, traversal paths are dropped;
- verification criteria do NOT ride in this context; the executor re-reads them from the mission task row at verification time.

## 3. The hosted audit input (`buildDeliverableAuditInput`)

The verifier receives the extracted deliverable, never the wrapper:

- framing header: "the reply text is a DELIVERY WRAPPER… fences are delivery syntax… audit THIS content";
- deliverable contract line (task id, kind, required files);
- citation contract line + the handed-off source list (documents);
- required-sections line (documents);
- **file inventory anchor**: every delivered file named with char counts (live-measured fix: the verifier claimed a file was missing from an input that contained it);
- the file contents, required/entry files first, per-file and total budget caps, excerpt markers honest ("present on disk, omitted from the audit excerpt for budget");
- honest NO-DELIVERABLE block when `parseFiles` extracted nothing.

The audit REQUEST additionally carries **deterministic pre-checks** — facts established mechanically over the exact same files (inventory, deliverable-file existence + heading/section counts, `auditPreview` static-site results, required-entry existence) — framed as settled evidence the audit must not re-litigate or contradict. The hosted audit's judgment adds content quality, contract fit and correctness ON TOP of settled facts.

Corrective revisions: the pipeline regenerates the FULL wrapper (existing streaming/buffered paths, same bounds), re-extracts, rebuilds both audit input and pre-checks, re-audits. Budgets and honesty outcomes are the pipeline's own (`maxAttempts`, `regenerationLimit`, `unverified`/`corrected-unverified`).

## 4. The document contract (the ten checks)

Run against `persisted.deliverableContent` (the executor's project-scoped load of the authorized path):

1. the required output file exists in the persisted workspace;
2. the authorized path is a safe project-relative path (traversal refused; boundary enforced by the executor's project-scoped load);
3. content non-empty and within limits (400–400,000 chars);
4. markdown structure: ≥ 2 section headings;
5. required sections present (case-insensitive heading match — the planner emits `Sources` when research was handed off);
6. numbered citations present (`[n]`, `[i, j]` clusters, bounded `[i-j]` ranges);
7. every marker index resolves to a handed-off source (1..n exactly as the handoff pack numbered them);
8. every URL in the document belongs to the handed-off pack (normalized like the handoff; unsupported URLs are named and refused);
9. missing or malformed source references fail (no Sources section listing any handed-off URL; out-of-range markers);
10. truncation cannot pass (unclosed code fence; sub-floor length).

Verified reason states the audit basis explicitly: "the persisted document itself passes the deliverable contract".

## 5. The website contract

Static websites are audited AS static sites — never a package.json demand, never an arbitrary stack requirement:

1. job-level gates first (real file changes ≥ contract, hosted self-verification status in the SUCCESS vocabulary `passed/pass/ok/success/clean/verified/corrected` — anything else blocks);
2. the persisted snapshot must exist (no snapshot ⇒ unproven, never verified);
3. required entry files (`requiredPaths`, default `index.html`) exist in the persisted workspace;
4. entry files carry substantive content (≥ 400 chars — HTML existence alone is not a verified website);
5. the existing `auditPreview` auditor runs over the persisted contents: no broken internal links, no missing assets, an entry HTML file exists;
6. no empty persisted files.

Verified reason names the audit basis: "persisted website audited as a static site — entry … with substantive content, N file(s), internal references resolve". Runtime browser behavior (navigation, responsiveness, console) is verified separately in the live product walk — never fabricated at verifier time.

## 6. Dispatch and normalization

- `verifyTaskOutput('code-build', criteria, …)` routes `criteria.deliverableKind === 'website'` to `verifyWebsiteBuild`; other code builds keep the job-payload gates (debug lane untouched).
- `document-draft` tasks are always `document`.
- `buildTaskSpec` normalization: kind-contradicting `deliverableKind` is a `MissionContractError`; `requiredPaths` must be safe project-relative files with extensions (≤ 6); `requiredSections` bounded (≤ 6 × 80 chars); legacy rows (no fields) parse to the kind-derived defaults.

## 7. Evidence and provenance

- The mission ledger stores ONLY verdicts and bounded reasons (`verificationResultJson` ≤ 4000 chars, secret-sanitized) — never deliverable content.
- The specialist job result carries `verification` (public summary: status/attempts/corrections/issuesFound), `verificationSkippedReason` (honest unavailability), and a bounded `missionTask` reference (ids + kind only).
- The Trust ledger receives evidence artifacts from verified outputs exactly as before.
