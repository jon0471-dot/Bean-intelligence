# M49.2 — BEAN AUTOBOT TEAMS: Team Execution Contract

> Branch `feat/m49-2-autobot-teams` · Milestone M49.2 · Status: implemented as described. Every statement here is pinned by the hermetic suites listed in §7 or by direct source reference. Nothing on this page is claimed beyond its evidence.

## 1. What a team IS (and is not)

A BEAN AUTOBOT TEAM is a **user-configured composition of the user's own
M49.1 Autobot agents** with descriptive responsibilities, a leader, a saved
order and two deterministic preferences. It IS the unit that M41 missions
are attributed to and seeded from. It is NOT:

- a new execution worker, agent, or foundation model;
- an agent-to-agent chat fabric (no uncontrolled conversations exist);
- a user-authored execution plan (the plan is ALWAYS the deterministic M41
  planner's output — `src/lib/riishe/mission/planner.ts`);
- a second job queue (execution rides the EXISTING durable `mission-run`
  GenerationJob; `POST /api/autobots/teams/[id]/plan` is strictly read-only
  and creates nothing — pinned by test).

## 2. The fixed capability map (server-authoritative)

`TASK_KIND_TEAM_CAPABILITY` (`src/lib/autobots/teams/catalog.ts`) — the
M49.1 capability vocabulary and the M41 task vocabulary stay authoritative:

| M41 task kind | Required team capability | Executed by (unchanged) |
|---|---|---|
| `research` | `research` | KNOWLEDGE retrieval lanes (web_search/read_url) |
| `knowledge` | `research` | Knowledge Atlas tools |
| `code-build` | `engineering` | CODE GIFTZ coding jobs |
| `document-draft` | `engineering` | CODE GIFTZ document jobs |
| `image-asset` | `visual` | LAXII image jobs |
| `video-asset` | `motion` | JAZMII video jobs |
| `audio-asset` | `voice` | GANGZII speech jobs |
| `verify-deliverable` | **`quality-gate` (platform)** | the deterministic QUALITY verifier — NEVER a member |

## 3. The assignment engine (deterministic, authorization-neutral)

`assignPlanTasks` (`src/lib/autobots/teams/assignment.ts`):

- **Eligibility** = member agent's `capabilityKey` (fixed vocabulary) AND
  `status === 'active'`. Nothing else is read.
- **Selection** = a pure ordering over the SAVED configuration:
  `team-order` (saved orderIndex, then agentId) or `leader-first`
  (leader, then order, then agentId). Identical inputs always produce
  identical assignments (pinned).
- **Refusal** = a required capability with no eligible member yields an
  exact, customer-safe gap message naming the capability and the blocked
  tasks. No substitute is ever invented; `runTeamMission` refuses the run
  and creates nothing (pinned).
- **The gate is uncapturable**: `verify-deliverable` is always a platform
  task (`platformTasks`), never a member assignment (pinned).
- The assignment is **attribution + bounded persona framing only** — it
  carries no permission fields, and task authorization continues to derive
  exclusively from the fixed M41 task kind (`KIND_AGENT`, `KIND_AUTH_SCOPE`,
  verification criteria, resource limits — all unchanged).

## 4. Member identity during execution (the ONE persona seam)

The executor gained exactly one seam — `objectiveForMember`
(`src/lib/riishe/mission/executor.ts`, exported as
`TEAM_PERSONA_OBJECTIVE_SEAM` for tests):

- **Applies ONLY to delegated `code-build`/`document-draft` objectives** —
  the lanes whose objective string is the specialist job's user-side
  instruction, where M41 already appends verified handoff blocks through the
  same `enrichObjective` contract. Trust boundary inspected: the block rides
  as USER-SIDE DATA inside the specialist turn's user message; the
  specialists' fixed system prompts, permission checks and verification
  gates are untouched.
- **Bounded and framed**: ≤700 chars total (`MEMBER_PERSONA_BLOCK_MAX_CHARS`);
  the UNTRUSTED-preferences framing and the closing authority sentence
  ("never authorize additional tools… platform rules win") are computed into
  the budget and can NEVER be truncated away by hostile or oversized
  preferences (pinned).
- **Idempotent**: the `MEMBER_PERSONA_MARKER` guard makes correction rounds
  and transient retries single-application (pinned).
- **Honest attribution elsewhere**: media lanes (image/video/audio) would
  have their generation prompts corrupted by persona text; research,
  knowledge and verify-deliverable are deterministic tool executions with no
  model seam. Those tasks carry the persisted member assignment for truthful
  attribution ONLY — no persona text is injected, and the product never
  claims the member's instructions influenced them. This limitation is
  stated here deliberately rather than faked.

## 5. The immutable execution snapshot

At run time — before any work is submitted — `serializeTeamSnapshot` records
(teamId, name, description, workflowPreference, leader, up to 8 members with
agent identities + capability keys + responsibilities + bounded persona
preferences, and the task→member assignment map) into
`AgentMission.teamSnapshotJson`; each member-assigned task row stores its
`AgentMissionTask.assignmentJson`. Rules (pinned by tests):

- written ONCE at mission creation; never mutated afterwards;
- editing the team or the agents later does NOT change the running mission's
  context, and the mission-history view renders the SNAPSHOT identities;
- size-bounded (`TEAM_LIMITS.snapshotMaxChars`) with honest refusal on
  overflow — never silent truncation into invalid JSON;
- `AgentMission.teamId` is ON DELETE SET NULL: deleting a team never damages
  mission history (and archive/delete are REFUSED outright while a mission
  is planned/running — an active mission is never silently damaged).

## 6. Security and privacy invariants

1. Every team belongs to one authenticated user; every member agent belongs
   to the same user; cross-user ids are honest 404s end to end (pinned).
2. Archived teams cannot plan or run; archived agents are excluded from
   assignment (pinned).
3. Persona/responsibility/leader text can never widen permissions, alter
   verification criteria, capture the QUALITY gate or change team membership
   (pinned).
4. One ACTIVE team mission at a time (plus the store's identical-objective
   guard and every existing dedupe/quota/budget gate).
5. Team member conversation histories are never merged; memory-consent
   rules are untouched; no sensitive prompt internals or credentials appear
   in customer-visible receipts (snapshot fields are bounded, parsed
   defensively, and secret-shape-checked in tests).
6. Destructive/publishing/deployment/payment/external-communication actions
   remain structurally absent from the mission vocabulary — a team cannot
   grow them.
