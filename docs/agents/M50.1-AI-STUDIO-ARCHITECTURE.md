## 1. What BEAN AI STUDIO is (and is not)

BEAN AI STUDIO is the planned visual node-based environment where users compose
AI workflows — nodes representing BEAN's REAL capabilities, connected by typed
ports — and execute them through the EXISTING governed infrastructure:
RIISHE's mission kernel, the durable GenerationJob queue, the capability
registry, the specialist products, the Trust Engine and the existing
authorization/quota/audit stack.

AI STUDIO **is not** (and the architecture below makes structurally difficult):

- a second AI platform, second orchestration core, or parallel inference path;
- a second job queue or a parallel workflow engine (execution compiles onto
  the ONE durable `mission-run` GenerationJob substrate — `src/lib/riishe/mission/store.ts`);
- a duplicate of the M41 mission executor or its verifiers;
- an arbitrary-code execution environment (no JavaScript/Python/shell/executable nodes — ever);
- an agent-to-agent chat fabric (coordination is the M41 DAG + structured
  verified handoffs, `src/lib/riishe/mission/handoff.ts`);
- NIIKI (M51 remains PLANNED; no NIIKI node exists in this design);
- a provider bypass (model/provider selection continues through the existing
  gateway + registry: `src/lib/router/router.ts`, `src/lib/registry/`).

**M50.1 freezes the architecture and contracts only.** The implementation
sequence M50.2–M50.7 is specified in §11. Nothing in this document authorizes
claims of a working Studio.

## 3. The planned product surface (M50 target experience)

The Studio product — when later milestones implement it — will expose ten
capabilities. Each is stated with its intended integration anchor so no later
milestone invents a new subsystem:

1. **Workflow Canvas** — visual node editor: pan, zoom, selection, alignment
   guides, typed connections. Client-side only; the graph is source-of-truthed
   server-side after save (§8). No execution authority in the browser.
2. **Node Library** — searchable catalogue rendered from a server-shared node
   registry (§5). The catalogue shows ONLY nodes whose substrate exists;
   unavailable capabilities appear as unavailable (registry health), never as
   working.
3. **Node Inspector** — per-node inputs, outputs, configuration schema,
   capability requirement, honest limitations and Trust requirements. Same
   discipline as the M49.1 agent inspector: what is shown is what the server
   enforces.
4. **Workflow Manager** — owner-scoped create, rename, duplicate, archive,
   restore, delete (guarded), organize (§8 lifecycle).
5. **Workflow Versions** — immutable versioned definitions; edits create a new
   draft version; publish freezes; rollback = run an older version (never a
   history rewrite).
6. **Validation Panel** — deterministic graph diagnostics (types, cycles,
   missing inputs, bounds, capability availability, permission status) from
   the pure validator (§6). Nothing here executes.
7. **Run Controls** — validate → preview (compiled plan, read-only) → run →
   cancel → inspect. The preview-then-confirm flow mirrors M49.2's
   `planTeamMission` (strictly read-only) → `runTeamMission` discipline.
8. **Execution Debugger** — per-node status/timing/inputs/outputs/artifacts/
   failure notes rendered from REAL `AgentMissionTask` rows of the backing
   mission (§9). No synthetic progress.
9. **Execution History** — previous runs with workflow version, honest
   outcome, usage and Trust receipts (the mission's `trustTaskId` ledger).
10. **Reusable Workflows** — duplicate-to-own templates; owner-scoped; no
    cross-user exposure of private graphs or artifacts.

### 3.1 User journey (design target)

1. User creates a workflow (`WorkflowDefinition`, draft v1) and places nodes
   from the library — e.g. `research.web` → `document.draft` → platform
   `quality.verify`.
2. Ports and edges are typed; the inspector shows each node's config (topic,
   prompt, deliverable path, size, voice) with the same bounds the server
   will enforce.
3. Save compiles nothing; Validate runs the pure validator and lists
   diagnostics (§6.2).
4. Preview shows the deterministic compiled plan: tasks, assigned specialists,
   dependency waves, the platform QUALITY gate, resource limits, and honest
   gaps (unavailable backend, missing input) — read-only, enqueues nothing.
5. Run submits: server re-validates, compiles, records the immutable
   version/execution references, and creates the mission through the EXISTING
   `createMissionFromPlan` — one durable `mission-run` job, Trust task, all
   existing gates.
6. The user watches real per-node progress (mission task rows), inspects real
   artifacts and verification verdicts, and opens deliverables in the EXISTING
   product surfaces (CODE GIFTZ project, LAXII/JAZMII/GANGZII histories) —
   the same follow-up links M49.2 team history already renders.
7. Terminal outcomes are honest: `completed`, `completed_partial`, `failed`,
   `cancelled` — decided by `decideMissionOutcome` on the deliverable chain.

### 3.2 Smallest UI integration point

The existing shell (`src/components/bean/shell.tsx`) owns navigation via the
`ViewId` union and the `NAV` array (groups: Platform / Products / Account;
`autobots` was added there in M49.1 as a first-class product). The smallest
consistent integration for AI STUDIO is **one new `ViewId` ('ai-studio') +
one NAV entry in the Products group + one view mount in `src/app/page.tsx`**,
exactly following the M49.1 autobots precedent — no navigation redesign, no
shell rewrite. This integration is itself implementation work (M50.4); M50.1
only freezes the choice.

## 4. Node contract and type system

### 4.1 Formal node contract (versioned)

Every node specification is a server-shared constant (imported by UI and
server, like `src/lib/autobots/catalog.ts` — the UI can never advertise a
node the server does not enforce). Contract fields:

```ts
interface StudioNodeContract {
  /** Stable, unique, slug-cased node type. Never reused across versions. */
  nodeType: string                      // e.g. 'research.web'
  /** Contract schema version for this node type. */
  contractVersion: 1
  displayName: string                   // customer-safe
  category: 'input' | 'research' | 'engineering' | 'media' | 'verification' | 'output'
  description: string                   // honest; includes limitations
  /** Exactly ONE M41 task kind — the fixed execution vocabulary. */
  taskKind: MissionTaskKind             // from src/lib/riishe/mission/types.ts
  inputs:  StudioPortSpec[]             // typed, required/optional
  outputs: StudioPortSpec[]
  /** Bounded config schema; validated server-side per node type. */
  configSchema: StudioConfigField[]
  /** Capability/registry surface whose availability gates this node. */
  capabilitySurface: BeanProductId | 'platform'   // from src/lib/registry/products.ts
  /** Existing approval requirements (Trust Engine), if any. */
  trustRequirement: 'standard-gates' | 'proposed-approval-gate'
  /** Deterministic verification criteria template (VerificationCriteria). */
  verification: VerificationCriteria
  /** Per-task resource limits, normalized through normalizeLimits(). */
  limits?: Partial<TaskResourceLimits>
  /** Whether the substrate exists today. Non-PROPOSED nodes only in M50.2+. */
  status: 'implemented-substrate' | 'proposed'
}
```

Rules pinned by this contract:

- `taskKind` is the ONLY bridge to execution. `buildTaskSpec`
  (`src/lib/riishe/mission/types.ts`) derives `agent` (`KIND_AGENT`) and
  `authScope` (`KIND_AUTH_SCOPE`) from the kind; a node contract cannot
  express, and the compiler cannot emit, any other agent or scope.
- `verification` flows through `normalizeVerificationCriteria`, whose existing
  kind-guards (e.g. a `document-draft` task can never declare a `website`
  deliverable kind) remain authoritative.
- `limits` are normalized by the existing caps (`TASK_LIMIT_CAPS`:
  executionTimeoutMs ≤ 20 min, maxAttempts ≤ 2, maxCorrections ≤ 1).
- `status: 'proposed'` nodes are inert: the registry may display them as
  planned, but the validator (§6) rejects any graph that contains one —
  unsupported node types are rejected, never silently substituted (§6.8).

### 4.2 Port type system (grounded in real BEAN contracts)

Port types correspond to data categories that ACTUALLY exist in the inspected
contracts. There are eight first-release types; a ninth is PROPOSED only:

| Port type | Grounded in | Producer of record | Consumer of record |
|---|---|---|---|
| `text` | `MissionTaskSpec.objective`/`params` strings (`MISSION_LIMITS.paramValueChars` 4000) | `input.text`, user config | any node's prompt/objective inputs |
| `json` | bounded `paramsJson` / config payloads | `input.text` (structured), configs | config inputs only (never an artifact port) |
| `research-pack` | `MissionTaskInputRef.artifact='research-pack'` | `research.web` | `document.draft` (cited handoff), `quality.verify` |
| `code-project` | `MissionTaskInputRef.artifact='code-project'` | `code.build`, `document.draft` | `quality.verify`, `output.deliverable` |
| `image-asset` | `MissionTaskInputRef.artifact='image-asset'` | `image.create` | `quality.verify`, `output.deliverable`, media reference inputs |
| `video-asset` | `MissionTaskInputRef.artifact='video-asset'` | `video.create` | `quality.verify`, `output.deliverable` |
| `audio-asset` | `MissionTaskInputRef.artifact='audio-asset'` | `audio.speech` | `quality.verify`, `output.deliverable` |
| `verification-result` | `TaskVerificationOutcome` (`{status, reasons[], artifacts[]}`) | `quality.verify` | `output.deliverable`, history/debug surfaces |
| `approval-ref` | **PROPOSED** — no mission task state exists for approval waits (§12) | — | — |

Compatibility rules (first release):

1. An edge must connect an output port to an input port of the SAME type.
   No coercion, no implicit conversion — the M41 handoff layer consumes the
   five artifact kinds above as-is (`researchPackFor`/`assetHandoff` in
   `src/lib/riishe/mission/{executor,handoff}.ts`), and `text` flows ride the
   bounded objective/param shaping the planner already performs.
2. `json` never feeds artifact ports; artifacts never feed `text` config ports
   directly (an asset reaches a prompt only through the M42 verified
   reference-block path — `preflightMediaReferences` in the executor — which
   the executor attaches; the graph expresses dependency, not prompt surgery).
3. Every edge becomes a `dependsOn` entry on the compiled consumer task
   (≤ `MISSION_LIMITS.maxDependenciesPerTask` = 6 per task); the M41 scheduler
   therefore never runs a consumer before its producers' outputs are VERIFIED
   (`readyTaskIds`, `src/lib/riishe/mission/graph.ts`).
4. Serialization boundary: everything crossing an edge is a bounded,
   customer-safe digest or a persisted artifact REFERENCE (project id / asset
   id / source URL) — never raw provider payloads, secrets, backend ids or
   local paths (`sanitizeEvidenceText` + bounded `artifactJson` in the store;
   handoff sanitization in `handoff.ts`).

## 6. Graph validation and execution compiler

### 6.1 Graph schema and identity

```jsonc
{
  "schemaVersion": 1,
  "nodes": [
    { "nodeId": "n1", "nodeType": "research.web", "contractVersion": 1,
      "config": { "topic": "…" }, "position": { "x": 0, "y": 0 } }
  ],
  "edges": [
    { "edgeId": "e1", "from": { "nodeId": "n1", "port": "pack" },
      "to": { "nodeId": "n2", "port": "research" } }
  ]
}
```

- `nodeId`: client-generated display id (`n1…`), unique per graph, length-
  bounded; it NEVER reaches execution — the compiler assigns task ids
  (`t1…` slug-safe per `buildTaskSpec`'s id rule) and records the
  nodeId→taskId map in the run record (§8.3).
- `nodeType` + `contractVersion` must resolve in the server registry at
  validation AND run time (no browser-supplied contracts — §7).
- `position` is presentation-only, never security-relevant.
- The versioned graph JSON is stored verbatim in the immutable
  `WorkflowVersion` (§8) — compilation is a pure, deterministic function of
  that stored text (same version + same registry ⇒ same compiled plan).

### 6.2 Validation stages (pure, deterministic, ordered)

1. **Schema**: `schemaVersion` supported; nodes/edges shape-valid; sizes
   within `WORKFLOW_LIMITS`.
2. **Registry resolution**: every `nodeType` exists with that
   `contractVersion`; unknown types are a hard error (never substituted).
3. **Port/edge typing**: endpoints exist; types match exactly (§4.2); ports
   cardinality valid.
4. **Cycle detection**: iterative DFS/Kahn — the M41 kernel's
   `validateTaskGraph`/`topologicalOrder` semantics applied to the compiled
   task list; a cyclic graph is invalid, loops are not supported.
5. **Required inputs**: every required input port is fed by an edge or a
   non-empty config value within bounds.
6. **Config validation**: per-node schema; text bounds mirror the task
   contract (`paramValueChars` 4000); media values validated against the SAME
   vocabularies the specialist submit paths enforce (`LAXII_SIZES`, video
   `1280x720|720x1280|1024x1024`, gangzii voices/limits — `specialists.ts`,
   `registry/products.ts`).
7. **Bounds**: node count, edges-per-node, projected per-task limits against
   `TASK_LIMIT_CAPS`; projected wall-clock against `MISSION_LIMITS.missionTimeoutMs`.
8. **Capability availability**: per-node `capabilitySurface` checked against
   registry health (`src/lib/registry/status.ts`, `capabilities.ts`) —
   surfaced as availability DIAGNOSTICS; the authoritative enforcement remains
   execution-time preflight (`preflight()` in the delegation paths). A
   validation pass is never a guarantee.
9. **Permission/status**: workflow owner check; archived definition/version
   refuses runs; unpublished (draft) versions refuse runs.
10. **Deliverable designation**: exactly one `output.deliverable` marker
    (or, equivalently, a single sink); otherwise invalid.

Output: `{ valid: boolean, problems: Diagnostic[] }` — customer-safe codes
(`E_SCHEMA`, `E_UNKNOWN_NODE`, `E_PORT_TYPE`, `E_CYCLE`, `E_MISSING_INPUT`,
`E_CONFIG`, `E_BOUNDS`, `E_CAPABILITY_UNAVAILABLE`, `E_PERMISSION`,
`E_DELIVERABLE`), each naming the offending node/port. Deterministic:
same graph ⇒ same diagnostics in the same order.

### 6.3 The compiler (the ONE new pure adapter)

`compileWorkflowToPlan(version, registry)` — PURE, deterministic:

- input: the immutable `WorkflowVersion.graphJson` + server node registry;
- output: a `MissionPlan`-shaped structure (tasks + deliverableTaskId) that
  `createMissionFromPlan` can consume, PLUS the nodeId→taskId map and the
  designated deliverable node id (stored on the run record, §8.3).

Compilation per node (the ONLY mapping table — server-authoritative, exactly
mirroring the M49.2 `TASK_KIND_TEAM_CAPABILITY` discipline):

| Node type | → MissionTaskSpec |
|---|---|
| `input.text` | no task — compiled into consumer task `params`/objective shaping (deterministic, bounded) |
| `research.web` / `knowledge.atlas` | `research` / `knowledge` task (`buildTaskSpec`) |
| `code.build` / `document.draft` | `code-build` / `document-draft` task |
| `image.create` / `video.create` / `audio.speech` | `image-asset` / `video-asset` / `audio-asset` task |
| `quality.verify` | `verify-deliverable` task (platform) |
| `output.deliverable` | no task — designates `deliverableTaskId` (the producing task of its connected port) |

Edges → `dependsOn` (consumer task depends on producer task; ≥1 edge
guarantees the M41 scheduler's verified-output ordering). Node config →
task `objective`/`params` through the SAME deterministic shaping helpers the
planner uses (`clip`, bounded extraction — `planner.ts`), never raw concatenation.

### 6.4 The mandatory QUALITY gate and deliverable designation

The compiler ALWAYS emits exactly one platform `verify-deliverable` task that
depends on every artifact-producing task of the workflow, mirroring all four
canonical M41 workflows. If the user placed `quality.verify` and
`output.deliverable` correctly, their mapping is used; if the user omitted the
gate, the compiler appends it — a user graph can never bypass verification.
`deliverableTaskId` = the task producing the deliverable marker's connected
artifact (fallback: the final artifact-producing task if the marker is
misplaced — the validator already rejects ambiguous markers, §6.2 item 10).

### 6.5 Critical architectural decision — how a visual graph becomes a governed run

Source evidence forces exactly one narrow design:

- The M41 TEXT planner (`planMission`) is a deterministic regex decomposer of
  FOUR canonical objectives with an honest refusal contract
  (`planner.ts`). It cannot and must not execute arbitrary user graphs — the
  Studio does NOT route through it, and no claim is made that it can.
- The M41 GRAPH KERNEL + STORE + EXECUTOR, however, are graph-agnostic by
  construction: `validateTaskGraph` validates ANY `MissionTaskSpec[]`;
  `createMissionFromPlan(userId, objective, plan)` persists ANY valid plan
  and enqueues ONE durable `mission-run` job; `runMissionJob` schedules ANY
  valid DAG through the existing specialist paths. The M49.2 team missions
  already proved the additive-context pattern (`teamId`/`teamSnapshotJson`/
  `assignmentJson` written once; ONE mission-run job; planner untouched).

**Therefore: the Studio's execution integration is a pure, deterministic
COMPILER (`compileWorkflowToPlan`) that turns a validated, immutable workflow
version into a `MissionPlan` consumed by the EXISTING
`createMissionFromPlan`.** Nothing else changes:

1. ONE planning-surface principle, restated precisely: M41's invariant is
   "deterministic, validated planning; no model-authored plans; no
   uncontrolled agent-to-agent chat". The compiler is a SECOND deterministic
   planning surface beside `planMission` (the first such addition, after
   M49.2 deliberately REUSED the text planner). It is authorized for M50 by
   the owner's AI STUDIO direction, and it is constrained to the SAME
   guarantees: every emitted task goes through `buildTaskSpec` (fixed kinds,
   fixed agents, fixed scopes, capped limits), every graph through
   `validateTaskGraph`, every run through the store's duplicate guard, Trust
   task, ONE mission-run job, the executor's verifiers and the platform
   QUALITY gate. The user authors WHAT connects to WHAT; the user can NEVER
   author a task kind, an agent, a scope, a permission or a verification
   criterion.
2. ONE queue: workflow runs ride the SAME `mission-run` GenerationJob on the
   riishe pool (`store.ts`). No workflow job type, no workflow queue, no
   workflow worker exists or may exist.
3. No duplicated specialists: delegated nodes submit through
   `submitSpecialistJob`/`delegateCoding` exactly as missions do; inline
   lanes (`research`/`knowledge`/`verify-deliverable`) run inside the
   mission-run driver exactly as they do today (`executor.ts`
   `INLINE_TASK_KINDS`/`DELEGATED_TASK_KINDS`).
4. Additive M41 vocabulary change required at M50.5 (PROPOSED): `MISSION_TYPES`
   gains `'workflow'` so the mission row's `missionType` honestly identifies
   the run's origin. The DB column is a plain String (`prisma/schema.prisma`),
   progress views render it verbatim, and existing four-type behavior is
   untouched — but the union is pinned by M41 tests, so M50.5 must extend and
   re-run them (§11 M50.5 acceptance).
5. Trust: `createMissionFromPlan` already creates the mission's Trust task
   (product riishe, kind `mission`); workflow runs inherit receipts, steps,
   evidence and approval gates with zero new ledger code.

Explicit non-designs (rejected, with reasons, so later milestones do not
re-litigate): driving graphs through `planMission` (impossible — fixed
refusal contract); a workflow-specific executor/queue (second engine —
forbidden); per-node GenerationJobs coordinated client-side (ungoverned —
forbidden); extending `MissionTaskSpec` with user-defined kinds (vocabulary
breach — forbidden).

### 6.6 Per-node and per-run state transitions (all inherited)

- Run = mission: `planned → running → completed | completed_partial | failed |
  cancelled` (CAS-validated; terminals immutable; failed/cancelled require a
  truthful note — `store.ts`).
- Node = mission task: `pending → ready → running → done | failed | skipped |
  cancelled` with the budgeted `failed → running` correction/retry seam.
- Workflow-level states (definition/version lifecycle) are Studio-owned and
  specified in §9.1; they never mask the mission's honest states.
- "A successful enqueue is never a successful execution" is enforced by the
  substrate itself: the mission becomes `running` only when the claimed job
  drives it, tasks settle only through verifier outcomes, and
  `decideMissionOutcome` never issues a premature verdict.

## 7. Security, Trust and ownership invariants

Every invariant below either already exists in inspected code (cited) or is a
binding M50 implementation requirement; none is optional.

1. **Owner scoping.** Workflow definitions, versions, runs and their histories
   belong to ONE authenticated user (`userId` on every row; every query
   owner-matched, exactly like `AutobotTeam`/`AgentMission` rows). Cross-user
   ids return honest 404s — never a existence leak (M49.2 precedent, pinned
   end-to-end by tests).
2. **Server-authoritative everything.** Node registry, port contracts,
   capability resolution, compilation, validation and authorization are
   server-side. The browser submits graph JSON as DATA; it can never supply
   node contracts, capabilities, permissions or plan fragments that the server
   trusts (the compiler re-reads the immutable stored version, never the
   request body).
3. **Validation AND execution-time checks.** Availability, permissions and
   limits are checked at validation (diagnostics) AND re-enforced at run
   submission AND re-enforced per delegated job by the existing
   `preflight()` gates — three independent layers, no browser claim trusted.
4. **No arbitrary code.** No JavaScript/Python/shell/executable node type may
   exist. Engineering work happens only inside CODE GIFTZ governed coding
   jobs under the project-write scope with versioned diffs and the restricted
   sandbox (`docs/agents/M41-AGENT-ARCHITECTURE.md` §2).
5. **No filesystem/network reach from nodes.** Node configs are bounded
   strings validated against per-node schemas; there is no node field that
   names a server path, URL fetch, socket or subprocess. Retrieval exists
   only as the governed `research`/`knowledge` lanes.
6. **No secrets.** Provider credentials never appear in prompts, logs, tool
   descriptions, browser code, node configs, compiled plans, run records or
   receipts (standing constraint, `AI_GUIDE.md`; `sanitizeEvidenceText` at
   the ledger boundary; backend ids stay in private registry modules).
7. **QUALITY gate uncapturable.** `verify-deliverable` maps to the platform
   execution path; no graph topology, config value, naming or user role can
   remove, replace or disable it — the compiler always emits it (§6.4), the
   verifier decides from REAL payloads (`verifiers.ts`), and the
   deliverable-chain outcome rule decides success (`graph.ts`).
8. **A workflow is not a permission escalation.** Connecting two nodes grants
   nothing: every compiled task's authority is `KIND_AUTH_SCOPE[taskKind]`
   (`project-write | asset-create | retrieval-read | mission-inspect`) — the
   same four bounded scopes missions use. No destructive, publishing,
   deployment, payment or external-communication scope exists to inherit.
   Running a workflow can never do more than its node types' kinds allow.
9. **Immutable versions and run snapshots.** `WorkflowVersion` rows are
   write-once (edits create new versions); a run pins its
   `workflowVersionId` and the compiled nodeId→taskId map at submission;
   later edits never change a running or historical run's meaning (the
   M49.2 immutable-snapshot rule, applied to workflow context).
10. **Bounded everything.** Graph size/edges/text per §5; per-task limits
    capped by `TASK_LIMIT_CAPS`; per-run wall clock by
    `MISSION_LIMITS.missionTimeoutMs`; parallelism by `takeParallelBatch`
    (≤3); retries/corrections budgeted; plus EVERY existing account-level
    gate: per-user active mission guards, duplicate refusal
    (`MissionDuplicateError`), specialist dedupe (`hasActiveDuplicate`),
    rate limits, daily quotas, budget guards, per-account workflow cap
    (PROPOSED: 50 definitions, mirroring the M49.1 agent cap).
11. **Safe serialization / untrusted framing.** Anything user-authored that
    later reaches a specialist prompt (configs, instructions) rides the same
    user-side, bounded, untrusted-framed channels missions already use
    (`enrichObjective` DATA blocks; the M49.2 persona-seam discipline is the
    precedent: bounded, framed, idempotent, never authorization-bearing).
    Diagnostic and receipt output is customer-safe (no backend identities,
    no provider names, no local paths).
12. **Audit + honest receipts.** Every consequential action rides the
    existing audit metering (`recordAudit`) and Trust Engine ledger; run
    receipts state what actually executed and verified — a queued submission
    is reported as queued, a failed node as failed, never as success.
13. **Rate limits & abuse.** Studio APIs reuse the service-level rate-limit
    pattern of `agent-service.ts`/`team-service.ts`; validation endpoints are
    pure and cheap but still rate-limited; run submission is the only
    enqueueing endpoint and inherits every quota/budget guard underneath.
14. **Deletion safety.** Deleting/archiving a definition with an ACTIVE run
    is refused (the run's mission continues or the refusal is explicit —
    never silently damaged; the M49.2 active-mission protection rule). Runs
    keep their historical meaning after any definition deletion via their
    pinned version snapshot.

## 8. Persistence and API contracts (PROPOSED — nothing created in M50.1)

### 8.1 Smallest durable model (3 tables; no migrations in this milestone)

The spec asks for the SMALLEST bounded model that reuses existing lifecycle.
The design below deliberately does NOT create `WorkflowNode` / `WorkflowEdge`
/ `WorkflowNodeRun` / `WorkflowArtifactReference` relational tables:

- Nodes and edges are the versioned definition's content — a bounded JSON
  document (`graphJson`, schema-validated, ≤65536 chars). A definition is
  edited and versioned as a whole; there are no per-node queries, writes or
  permissions that would justify relational rows.
- Per-node RUN state already has a home: `AgentMissionTask` rows of the
  backing mission. The nodeId→taskId map pinned on the run row makes the
  mapping exact; a second per-node ledger would duplicate the mission ledger
  (forbidden duplication).
- Artifacts already have a home: `AgentMissionTask.artifactJson` /
  `verificationResultJson` and the product asset tables (`CodeProject`,
  `ImageAsset`, `GangziiAudioAsset`, `JazmiiProduction`…). A workflow artifact
  table would be a second books-keeping of the same objects.

```prisma
model WorkflowDefinition {           // PROPOSED — not created in M50.1
  id          String   @id @default(cuid())
  userId      String
  user        User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  name        String   // ≤80, normalized like team names
  description String?  // ≤600
  status      String   @default("active") // active | archived
  versions    WorkflowVersion[]
  runs        WorkflowRun[]
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
  @@index([userId, status])
}

model WorkflowVersion {              // PROPOSED — immutable after publish
  id            String   @id @default(cuid())
  definitionId  String
  definition    WorkflowDefinition @relation(fields: [definitionId], references: [id], onDelete: Cascade)
  version       Int      // 1..n, monotonic per definition
  status        String   @default("draft") // draft | published | superseded
  graphJson     String   // bounded, schemaVersion-tagged graph (§6.1)
  changeNote    String?  // ≤300
  publishedAt   DateTime?
  createdAt     DateTime @default(now())
  @@unique([definitionId, version])
  @@index([definitionId, status])
}

model WorkflowRun {                  // PROPOSED — thin reference row
  id                String   @id @default(cuid())
  userId            String
  definitionId      String
  definition        WorkflowDefinition @relation(fields: [definitionId], references: [id], onDelete: Cascade)
  versionId         String   // the pinned immutable version
  missionId         String   @unique // the REAL execution ledger (AgentMission)
  objective         String   // ≤4000 (MISSION_LIMITS.objectiveChars)
  compiledPlanJson  String   // nodeId→taskId map + deliverable node/task ids (bounded)
  status            String   @default("planned") // mirrors the mission status honestly
  failureNote       String?  // truthful, when failed/cancelled
  createdAt         DateTime @default(now())
  finishedAt        DateTime?
  @@index([userId, createdAt])
  @@index([definitionId, createdAt])
}
```

Notes:

- `WorkflowRun.status` is a DERIVED mirror of the mission status (updated by
  the same settlement paths or read-through) — the mission remains the
  single lifecycle authority. No workflow-side transitions exist that could
  contradict the mission ledger.
- Deletion/archival semantics: archiving a definition hides it from creation
  surfaces; active runs block archive/delete (§7.14); deleting a definition
  cascades versions but missions/history survive through `AgentMission`
  (which is NOT workflow-owned) — run rows may cascade with the definition
  while the mission ledger persists, or be retained by policy; exact behavior
  is an M50.3 acceptance item.
- Retention/cleanup: proposed defaults — runs visible 90 days, then
  prunable while missions retain their own ledger semantics; final numbers
  are an owner decision at M50.3.
- Identity boundaries: single-user product (the existing `User` model;
  no organizations exist in this application — no org columns are invented).

### 8.2 API contracts (PROPOSED; conventions follow `src/app/api/autobots/**`)

| Endpoint | Method semantics |
|---|---|
| `GET /api/ai-studio/workflows` | owner-scoped list (name/description/status/versions-latest/active-run flag); `take` ≤50 |
| `POST /api/ai-studio/workflows` | create definition + draft v1 (bounded normalization; 422 on vocabulary/bounds violations; account cap enforced) |
| `GET /api/ai-studio/workflows/[id]` | definition + version list + derived stats (run count, last outcome) |
| `PATCH /api/ai-studio/workflows/[id]` | rename/describe/archive/restore (409 while an active run exists, per §7.14) |
| `DELETE /api/ai-studio/workflows/[id]` | guarded delete (409 with active runs) |
| `POST /api/ai-studio/workflows/[id]/duplicate` | deep copy → new definition with draft v1 of the latest graph (owner = caller; duplicates never cross owners) |
| `POST /api/ai-studio/workflows/[id]/versions` | new draft from a published version (safe-edit start) |
| `POST /api/ai-studio/workflows/[id]/versions/[v]/publish` | validate; freeze draft → published (immutable); prior published → superseded |
| `POST /api/ai-studio/workflows/[id]/versions/[v]/validate` | PURE validation (§6.2) — creates nothing, enqueues nothing (M50.2 must pin this by test, exactly like M49.2's read-only plan preview) |
| `POST /api/ai-studio/workflows/[id]/versions/[v]/preview` | read-only compiled-plan preview (tasks, specialists, waves, gate, limits, gaps) — no rows written |
| `POST /api/ai-studio/workflows/[id]/versions/[v]/run` | re-validate → compile → create WorkflowRun + mission via `createMissionFromPlan` (201 `{runId, missionId, jobId}`); duplicate-run protection = the store's active-duplicate guard + one-active-run-per-definition guard (PROPOSED, mirroring M49.2) |
| `GET /api/ai-studio/workflows/[id]/runs` | owner-scoped run history (take ≤50) |
| `GET /api/ai-studio/runs/[id]` | run detail: honest status, per-node states/verification outcomes/artifacts (mission-backed), Trust receipt linkage, version pin |

Error semantics: 401 unauthenticated; 404 foreign/nonexistent ids (honest,
no existence leak); 422 validation with the §6.2 diagnostic codes and
bounded messages; 409 duplicate/archived/active-run conflicts; 429 rate
limits (existing infrastructure, standard headers); 503 when a required
specialist backend is unavailable at submission preflight — the mission-side
honest failure remains the deeper truth for later backend loss.

### 8.3 Reused vs new (explicit ledger)

REUSED (no new code, no duplication): `AgentMission`/`AgentMissionTask`
lifecycle + CAS; the ONE `mission-run` GenerationJob; specialist delegation

## 9. Debugging, history and honest failure states

### 9.1 Workflow-level states (Studio-owned, never masking execution truth)

- **Definition**: `active | archived` (+ deletion guarded by active runs).
- **Version**: `draft → published → superseded` (publish is the freeze
  point; drafts are the only editable state; superseded versions remain
  runnable/readable for rollback and history — no rewrite, no deletion of
  published versions while any run references them).
- A version is never "valid/invalid" as a stored state — validity is a
  DETERMINISTIC FUNCTION recomputed on demand (validate/preview/publish/run),
  because registry availability changes over time. Persisting a validity
  bit would rot; the architecture forbids it.

### 9.2 Run and node lifecycles (inherited verbatim from M41)

- Run: `planned → running → completed | completed_partial | failed |
  cancelled` (§6.6). Every terminal state carries its bounded truthful
  summary/note (`outcomeSummary`/`failureNote`).
- Node: `pending → ready → running → done | failed | skipped | cancelled`
  with budgeted retry/correction re-entry; `skipped` marks unexecuted
  downstream work after an upstream failure — an unexecuted node is never
  displayed as executed (`skippedDownstream`, `graph.ts`).
- **Waiting-for-approval**: NOT available in the first release. The Trust
  task lifecycle supports `waiting_for_approval`, and the approval API
  exists (`approvals.ts`), but the MISSION task vocabulary has no
  approval-wait state and the executor has no pause seam (§5 PROPOSED
  `approval.gate`). A workflow needing human approval mid-run cannot be
  expressed yet — the catalogue/validator must say so, not fake it.
- Delegated node detail: after the specialist job is submitted, the node's
  live state is the REAL delegated job's state (`specialistJobId` link on
  the task row; the mission executor polls job completion and classifies
  honest error classes — transient `rate_limited|network|timeout|
  worker_lost` vs permanent). The Studio debugger renders that state, never
  a local approximation.

### 9.3 Honesty rules (each enforced by cited substrate)

| Rule | Enforcement (source of truth) |
|---|---|
| A planned node is never a completed node | task lifecycle CAS transitions (`store.ts`) |
| A queued/accepted submission is never a finished execution | `attachSpecialistJob` + polling + verifier settlement (`executor.ts`); specialists' own "never claim ready" contract (`specialists.ts` tool descriptions) |
| A generated artifact is not a verified deliverable until verification confirms it | `verifiers.ts` deterministic outcomes; `artifactJson` written only from admitted artifacts; `decideMissionOutcome` deliverable-chain rule (`graph.ts`) |
| No fake progress, no synthetic history | the Studio UI reads ONLY `AgentMission`/`AgentMissionTask`/`GenerationJob` rows and Trust receipts; M50.6 must pin "no run row without a mission row" by test |
| Partial completion is stated, not hidden | `completed_partial` semantics + side-failure reasons (`graph.ts`); M49.2 history rendering is the precedent |
| Cancellation is propagated, not orphaned | `requestMissionCancel` → executor propagation → task `cancelled` states (`store.ts`/`executor.ts`) |
| Crash recovery | the mission-run job's claim/lease/heartbeat/recovery + `settleOrphanedRunningMissions` (`jobs/queue.ts`, `executor.ts`) — inherited by workflow runs without new code |

### 9.4 Debugger surface contract (design)

Per node: status, started/finished timestamps, duration, attempts/corrections,
verification verdict + reasons, admitted artifact references (customer-safe:
project/asset ids, servable URLs), delegated job link (customer-safe states),
failure note. Per run: version pin (renderable diff against the definition's
current draft), objective, outcome summary, Trust receipt link, usage
metering (existing usage records). Failure reasons are bounded,
customer-safe strings — never raw stack traces, provider payloads or prompt
internals.

## 10. UI architecture and responsiveness (design for M50.4)

### 10.1 Dependency truth (inspected `package.json`)

The repository has NO graph/canvas library (no React Flow, no dgrl/X6, no
konva). It DOES have: `zustand` (client state), `@dnd-kit/core|sortable|
utilities` (drag interactions), the full Radix primitive set, `lucide-react`,
`react-resizable-panels`, `@tanstack/react-query`, `tailwindcss`. Per the
M50.1 constraint ("recommend suitable existing UI dependencies only after
inspecting the repository's current package and dependency choices. Do not
introduce a new library in this milestone"):

- **M50.1 recommendation**: build the canvas as an SVG/DOM layer on EXISTING
  dependencies — `zustand` for canvas/graph state (nodes, selection, viewport,
  transient connection state), pointer events for pan/zoom (a bounded,
  testable custom hook), SVG for edges (typed stroke styles per port type),
  Radix Popover/Tooltip/Select/Dialog for the inspector/library/validation
  panel, `@dnd-kit` for palette→canvas placement, `react-resizable-panels`
  for the canvas/inspector layout, `@tanstack/react-query` for server state.
  This is honest: a first-release node graph (≤9 nodes) does not need a
  heavy graph engine, and the repo's anti-dependency posture (zero recurring
  cost, minimal surface) favors it.
- **M50.4 decision point (requires owner approval)**: IF implementation
  evidence shows the hand-built canvas costs more than a dedicated library,
  introducing one (e.g. React Flow) is a scoped, owner-approved dependency
  addition at M50.4 — not before, not silently.

### 10.2 Canvas behavior (design)

- Layout: three-region shell (library rail | canvas | inspector), two-panel
  on narrow desktop; `react-resizable-panels`.
- Canvas: viewport transform (pan/zoom with clamped scale), grid, selection
  (click/shift/marquee), alignment guides, typed connection dragging with
  port-compat highlighting (live feedback from the §4.2 rules), edge
  deletion, node duplication.
- Palette: searchable, category-grouped, registry-driven; PROPOSED/unsupported
  nodes either hidden or rendered with an explicit planned badge and
  non-placeable behavior (they can never enter a graph — §5).
- Inspector: contract-driven form generation from `configSchema` with the
  same bounds server-side validation enforces; capability chip showing
  measured availability (registry), honest "unavailable" states.
- Validation feedback: inline diagnostics (node/edge markers) + panel list;
  deterministic codes from §6.2; publish/run blocked until valid.
- Execution highlighting: colors driven by REAL run states (§9) fetched by
  polling the run endpoint; no optimistic execution coloring.
- States to design explicitly: empty (no workflows / no nodes), loading,
  error, unavailable (backend health), permission-denied, archived
  definition, active-run read-only edits, version-mismatch (viewing an old
  version's graph), draft vs published badges.

### 10.3 Keyboard accessibility (design)

Node traversal (tab/arrows), port-to-port connection via keyboard
(enter/space workflow), delete/escape semantics, zoom shortcuts with
documented keymap, focus rings, ARIA roles for nodes/edges (listbox/graph
descriptions), full validator diagnostics also exposed as text (screen-reader
usable). Canvas operations must degrade to form-based editing (the inspector
allows building the same graph without pointer gestures) — accessibility
fallback, not a separate product.

### 10.4 Mobile strategy (honest)

A freeform node canvas on a small touchscreen cannot honestly deliver the
same editing experience. The responsive strategy: desktop/tablet-landscape =
full canvas; small screens = READ-ONLY surfaces (workflow list, version
graph as a vertical dependency list/stepper, run progress per node,
validation diagnostics, history) with a clear "edit on a larger screen"
state, PLUS the form-based editor (§10.3 fallback) available for bounded
edits (config values, rename) — no pretend pinch-zoom canvas, no hidden
desktop-only traps. M50.7 acceptance must exercise both surfaces on real
device profiles.
