# HTTP Caching Technical Report

## Introduction

HTTP caching is a fundamental mechanism for improving web performance by reducing latency and network bandwidth usage. By storing responses to HTTP requests and reusing them when possible, caching systems can significantly accelerate content delivery. This report provides a comprehensive technical analysis of HTTP caching mechanisms, including browser cache, CDN caching, and proxy caches, along with key directives and validation methods.

## Browser Cache

Browser caching occurs locally on the client machine, allowing web browsers to store responses to previously made requests. When a user revisits a website, the browser can serve content from its local cache instead of making new HTTP requests to the server.

The browser cache typically stores two types of resources:
- **Persistent cache**: Stored on disk and survives browser sessions
- **Session cache**: Stored in memory and cleared when the browser closes

Browser caching operates based on HTTP headers provided by the server. The most important headers for browser caching are:
- `Cache-Control`
- `Expires`
- `Last-Modified`
- `ETag`

Modern browsers implement sophisticated cache eviction policies, typically based on:
- LRU (Least Recently Used) algorithm
- Resource size (prioritizing smaller resources)
- Access frequency
- Content type (HTML, CSS, JavaScript, images, etc.)

When a browser makes a request, it first checks its cache. If a valid cached response exists, the browser uses it without contacting the server. This is known as a cache hit. If no valid cached response exists, the browser makes a new request to the server, which may respond with a new resource or an instruction to revalidate the existing cached resource.

## CDN Caching

Content Delivery Networks (CDNs) are distributed systems of proxy servers deployed across multiple data centers. CDNs cache content closer to end users, reducing latency and improving load times for global audiences.

CDN caching operates at the edge of the network, typically at internet exchange points and access networks. When a user requests content, the CDN serves it from the nearest edge location rather than the origin server.

Key characteristics of CDN caching:
- **Geographic distribution**: Multiple edge locations worldwide
- **Caching at multiple levels**: From edge servers to mid-tier caches
- **Cache hierarchies**: Multiple cache layers with different eviction policies
- **Cache invalidation strategies**: Time-based, content-based, and event-based

CDNs implement sophisticated cache key generation, often including:
- URL path and query parameters
- Hostname
- Request headers (Accept-Language, Accept-Encoding)
- Custom cache keys based on business logic

CDNs also offer advanced features like:
- **Cache purging**: Immediate removal of content from the cache
- **Cache warming**: Proactively populating the cache with expected content
- **Cache fragmentation**: Serving different content based on request characteristics
- **Origin shield**: Reducing load on origin servers by using mid-tier caches

## Proxy Caches

Proxy caches sit between clients and servers, intercepting HTTP requests and serving cached responses when possible. They can be deployed at various levels:

1. **Forward proxies**: Used by clients to access the internet, often in corporate or educational networks
2. **Reverse proxies**: Used by servers to distribute load, improve performance, and provide security
3. **Transparent proxies**: Operate without explicit client configuration

Proxy caches offer several advantages:
- Bandwidth reduction by serving repeated requests
- Improved response times for subsequent requests
- Reduced load on origin servers
- Enhanced privacy in some configurations

Proxy caches implement complex cache key generation that may include:
- URL and query parameters
- Host header
- Request headers (Accept, Accept-Language, etc.)
- Authentication status
- Content negotiation headers

Proxy caches also implement sophisticated cache consistency models:
- **Consistent hashing**: Distributing cache entries across multiple proxy servers
- **Cache partitioning**: Dividing the cache namespace into logical segments
- **Cache replication**: Replicating popular content across multiple proxy servers

## Cache-Control Directives

The `Cache-Control` header is the primary mechanism for controlling caching behavior. It consists of directives that specify caching policies for both requests and responses.

### Key Cache-Control Directives

1. **public**: Indicates the response can be cached by any cache, including shared caches like CDNs and proxies
2. **private**: Indicates the response can only be cached by private caches (e.g., browser cache)
3. **no-cache**: Forces caches to validate with the origin server before using a cached response
4. **no-store**: Prevents caches from storing any part of the response
5. **max-age**: Specifies the maximum time a response can be considered fresh (in seconds)
6. **s-maxage**: Like max-age, but applies only to shared caches (overrides max-age)
7. **must-revalidate**: Requires caches to obey max-age and validation directives strictly
8. **proxy-revalidate**: Similar to must-revalidate, but applies only to shared caches
9. **no-transform**: Prohibits caches from modifying the response content (e.g., gzipping images)
10. **only-if-cached**: Instructs caches to return only cached responses without contacting the origin

### Example Cache-Control Headers

```
# Cache for 1 hour, can be stored by any cache
Cache-Control: public, max-age=3600

# Cache for 1 day in browser only, must validate after
Cache-Control: private, max-age=86400, must-revalidate

# Don't cache at all
Cache-Control: no-store

# Cache but must validate before use
Cache-Control: no-cache
```

## ETags and Validation

Entity tags (ETags) are unique identifiers assigned to resources by servers. They provide a mechanism for cache validation, allowing caches to determine if a cached response is still current without retransmitting the entire response.

### ETag Generation

ETags can be generated in various ways:
- **Content-based**: Hash of the response content
- **Timestamp-based**: Modified time of the resource
- **Version-based**: Version number or revision identifier
- **Inode-based**: File system inode number (for static resources)

### Validation Process

When a cache needs to validate a cached response, it sends a conditional request with the `If-None-Match` header containing the ETag:

```
GET /resource HTTP/1.1
If-None-Match: "33a64df551425fcc55e4d42a148795d9f25f89d4"
```

The server responds with:
- `304 Not Modified` if the resource hasn't changed (cache can use its stored response)
- `200 OK` with the new resource if the resource has changed

### Last-Modified Headers

The `Last-Modified` header provides an alternative validation mechanism using the timestamp of the last modification:

```
GET /resource HTTP/1.1
If-Modified-Since: Wed, 21 Oct 2015 07:28:00 GMT
```

The server responds with:
- `304 Not Modified` if the resource hasn't been modified since the specified time
- `200 OK` with the new resource if the resource has been modified

## Stale-While-Revalidate

The `stale-while-revalidate` directive (part of the `Cache-Control` header) allows caches to serve stale content while asynchronously revalidating it with the origin server.

This mechanism provides improved performance in scenarios where:
- The origin server is experiencing high latency
- The content doesn't change frequently
- Users prioritize speed over absolute freshness

When a cache receives a request for content that is stale but has `stale-while-revalidate` set, it:
1. Serves the stale cached response immediately
2. Sends a background request to revalidate the content
3. Updates the cache with the new response when available

Example:
```
Cache-Control: public, max-age=600, stale-while-revalidate=3600
```

In this example:
- The content is considered fresh for 600 seconds (10 minutes)
- After becoming stale, it can still be served for up to 3600 seconds (1 hour) while being revalidated

## Conclusion

HTTP caching is a critical component of modern web infrastructure, providing significant performance benefits through various mechanisms. Understanding the different caching layers—from browser caches to CDNs and proxy caches—enables developers and architects to design systems that optimize for both performance and consistency.

The proper use of `Cache-Control` directives, along with validation mechanisms like ETags and `Last-Modified`, allows for precise control over caching behavior. Advanced techniques like `stale-while-revalidate` provide additional flexibility, allowing systems to balance freshness with performance requirements.

By implementing effective caching strategies, organizations can reduce bandwidth costs, improve user experience, and enhance the scalability of their web applications.# HTTP Caching Technical Report
