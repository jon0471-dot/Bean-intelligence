# HTTP Caching Technical Report

## Introduction

HTTP caching is a fundamental mechanism for reducing latency and network traffic while improving website performance. By storing copies of responses and reusing them when possible, caching systems can significantly reduce the number of round trips between clients and servers, resulting in faster load times and reduced bandwidth consumption. This report provides a detailed technical examination of HTTP caching mechanisms, including browser cache, CDN caching, proxy caches, and various caching directives.

## Browser Cache

Browser caching occurs when a web browser stores local copies of resources previously requested from a server. Modern browsers implement sophisticated caching mechanisms that store resources on the client's disk or in memory for quick retrieval.

The browser cache operates through several key components:

1. **Cache Storage**: Browsers typically use two storage mechanisms:
   - Disk-based storage for persistent caching across sessions
   - Memory-based storage for temporary caching during a single browsing session

2. **Cache Key**: The combination of the request URL and the Vary header fields determines the cache key. Resources with different Vary headers are stored as separate entries.

3. **Cache Hit vs. Cache Miss**: 
   - A cache hit occurs when the browser finds a valid cached response for a request.
   - A cache miss occurs when no valid cached response exists, requiring a new request to the server.

4. **Cache Invalidation**: Browsers use various strategies to determine when cached resources should be considered stale:
   - Expiration times set via headers
   - Validation requests using ETags or Last-Modified headers
   - Manual cache clearing by users

Browser caching is particularly effective for static resources like images, CSS, JavaScript files, and fonts, which change infrequently.

## CDN Caching

Content Delivery Networks (CDNs) are distributed systems of proxy servers that cache content closer to end users. CDN caching operates at a larger scale than browser caching and serves multiple users across different geographic locations.

Key aspects of CDN caching include:

1. **Edge Caching**: CDNs place caching servers at network edge locations, reducing the physical distance between users and cached content.

2. **Cache Hierarchy**: CDNs typically implement multiple cache layers:
   - Edge caches (closest to users)
   - Mid-tier caches
   - Origin caches (closest to the origin server)

3. **Cache Invalidation Strategies**: 
   - Time-based expiration
   - Purge/refresh mechanisms
   - Pre-positioning of popular content

4. **Content Negotiation**: CDNs can cache different versions of content based on request headers, such as Accept-Language for language-specific content.

CDNs are particularly effective for:
- Static content delivery
- Reducing origin server load
- Handling traffic spikes
- Improving performance for global audiences

## Proxy Caches

Proxy caches sit between clients and servers, intercepting HTTP requests and serving cached responses when possible. They can be deployed at various levels:

1. **Forward Proxies**: 
   - Used by organizations to cache content for internal users
   - Can filter requests and cache responses
   - Often used to bypass restrictions or improve performance

2. **Reverse Proxies**:
   - Sit in front of origin servers
   - Cache responses from the server
   - Provide additional benefits like load balancing and security

3. **Public Proxy Caches**:
   - Operated by ISPs or third parties
   - Cache content for multiple users
   - Can improve performance for users with limited bandwidth

Proxy caches must handle cache validation carefully, as they serve multiple users who may have different permissions or access levels to the same resource.

## Cache-Control Directives

The Cache-Control header is the primary mechanism for controlling caching behavior. It consists of various directives that specify how caches should handle responses.

### Important Cache-Control Directives:

1. **max-age**: Specifies the maximum time a response can be considered fresh, in seconds.
   - Example: `Cache-Control: max-age=3600` (1 hour)

2. **no-cache**: Forces caches to validate with the origin server before using a cached copy.
   - Does not mean "don't cache" but rather "revalidate before use"

3. **no-store**: Prevents caching of the response or any portion of it.
   - Used for sensitive data that should never be stored

4. **public**: Indicates the response can be cached by any cache, even if normally non-cacheable.
   - Useful for responses containing user-specific information that's safe to cache

5. **private**: Indicates the response is intended for a single user and should not be cached by shared caches.
   - Default for responses containing user-specific information

6. **must-revalidate**: Once a resource becomes stale, caches must not use it without validation.
   - Ensures strict compliance with freshness requirements

7. **proxy-revalidate**: Similar to must-revalidate but applies only to shared (proxy) caches.

8. **s-maxage**: Like max-age but applies only to shared caches, overriding max-age.
   - Example: `Cache-Control: public, s-maxage=60, max-age=300` (CDNs cache for 1 minute, browsers for 5 minutes)

## ETags and Validation

Entity tags (ETags) are unique identifiers assigned to representations of resources. They provide a mechanism for cache validation without requiring the entire resource to be transferred.

### ETag Operation:

1. **Initial Request**: Server responds with an ETag in the ETag header.
   - Example: `ETag: "33a64df551425fcc55e4d42a148795d9f25f89d4"`

2. **Subsequent Request**: Client includes the ETag in the If-None-Match header.
   - Example: `If-None-Match: "33a64df551425fcc55e4d42a148795d9f25f89d4"`

3. **Server Validation**: 
   - If the resource hasn't changed, server responds with 304 Not Modified
   - If the resource has changed, server responds with the full new resource and a new ETag

### Last-Modified Validation:

An alternative to ETags is the Last-Modified header, which uses the last modification date of the resource:

1. **Initial Request**: Server responds with Last-Modified header.
   - Example: `Last-Modified: Wed, 21 Oct 2015 07:28:00 GMT`

2. **Subsequent Request**: Client includes the Last-Modified date in the If-Modified-Since header.
   - Example: `If-Modified-Since: Wed, 21 Oct 2015 07:28:00 GMT`

3. **Server Validation**: 
   - If the resource hasn't been modified since the specified date, server responds with 304 Not Modified
   - Otherwise, server responds with the full new resource

ETags are generally preferred over Last-Modified because:
- They can detect more subtle changes (e.g., byte-for-byte identical but regenerated content)
- They avoid issues with clock synchronization between client and server
- They can be more efficient for resources with frequently changing modification times

## Stale-While-Revalidate

The stale-while-revalidate directive allows caches to serve stale content while asynchronously checking for a newer version. This improves performance by reducing latency for cached content.

### Operation:

1. **Cache with Stale Content**: When a request arrives and the cache has stale content (past its freshness lifetime but not yet expired).

2. **Serve Stale Content**: The cache serves the stale response immediately.

3. **Background Revalidation**: The cache sends a validation request to the origin server in the background.

4. **Update Cache**: If the server responds with a newer version, the cache updates its stored response for future requests.

The directive is specified as:
```
Cache-Control: stale-while-revalidate=60
```
This means the cache can serve stale content for up to 60 seconds after it becomes stale while performing background revalidation.

This approach is particularly useful for:
- Content where absolute freshness isn't critical
- Resources with high latency origin servers
- Reducing perceived latency for users

| no-store | Never cache the response | `Cache-Control: no-store` |
| public | Can be cached by any cache | `Cache-Control: public` |
| private | Only for single user, not shared caches | `Cache-Control: private` |

| stale-while-revalidate | Serve stale while revalidating | `Cache-Control: stale-while-revalidate=60` |
| stale-if-error | Serve stale if error occurs | `Cache-Control: stale-if-error=3600` |

## Conclusion

HTTP caching is a critical component of modern web performance optimization. By understanding the various caching mechanisms—from browser caches to CDNs and proxy caches—and properly utilizing caching directives, developers can create faster, more efficient web applications. The careful use of ETags, validation mechanisms, and advanced directives like stale-while-revalidate allows for fine-tuned control over caching behavior.
